# Выжимка хакатона: кейс, критерии, правила, ресурсы

Источники: кейс «Единый кейс по геймификации практических заданий» (HackAlem AI, трек AI Sana, владелец задачи — МНВО, AI Sana) и материалы организаторов (правила, инструкция участника, активация OpenAI и NVIDIA, оборудование, кибербезопасность, курс ASU). Здесь только то, что влияет на нашу работу.

## 1. Кейс в одном абзаце

За 5 часов сделать работающий MVP (веб-приложение), в котором представитель бизнеса превращает короткое описание задачи в полноценную карточку, система считает рейтинг готовности 0–100 и публикует карточку в открытом каталоге. Студенческие команды сами выбирают задачи и откликаются, бизнес сам выбирает, с кем работать. Главная геймификация направлена на бизнес: чем полнее и полезнее описана задача, тем выше её рейтинг и место в каталоге.

Формально команда — 3–5 человек, у нас двое. Поэтому роли разделены жёстко (`docs/team/`), а рутину делают AI-агенты.

## 2. Сквозной сценарий (обязателен и проверяется на демо)

| Шаг | Действие | Что должно работать в MVP |
| :-: | --- | --- |
| 1 | Черновик | Бизнес вводит краткое описание потребности или задачи |
| 2 | Уточнение | Система находит недостающие сведения и задаёт не менее 3 уместных вопросов |
| 3 | Карточка | Из ответов собирается редактируемая карточка, бизнес её подтверждает |
| 4 | Рейтинг | Баллы за полноту и подсказки, что поднимет рейтинг |
| 5 | Каталог | Подтверждённая задача публикуется на позиции, соответствующей рейтингу |
| 6 | Выбор студентов | Любая команда смотрит каталог или рекомендации и подаёт предложение |
| 7 | Выбор бизнеса | Бизнес сравнивает предложения и сам выбирает одну, несколько или ни одной команды |
| 8 | Результат | После подтверждённого этапа выбранная команда получает баллы за прогресс |

На защите: вводим слабое описание, дополняем, показываем рост рейтинга, публикуем, команда откликается, бизнес вручную принимает или отклоняет. Все переходы должны работать в MVP, а не на слайдах.

## 3. Обязательный функционал и где он у нас

| Модуль | Минимальное требование кейса | Где реализуем |
| --- | --- | --- |
| Конструктор задачи | Свободный ввод, проверка полноты, не менее 3 вопросов, редактируемая карточка, ручное подтверждение | `POST /api/tasks`, `/answers`, `PATCH /card`; экран-мастер у B |
| Карточка задачи | Название, контекст, потребность, пользователи, данные, ограничения, ожидаемый результат, критерии успеха, контакт, формат взаимодействия | 10 полей, см. `docs/rating-and-gamification.md` |
| Рейтинг задачи | 0–100, расшифровка баллов, список недостающего, пересчёт после правки | `backend/app/domain/rating.py` + панель рейтинга |
| Общий каталог | Все опубликованные задачи видны всем; сортировка по рейтингу; фильтры по теме и уровню | `GET /api/catalog` + страница каталога |
| Отклики команд | Идея, план, ссылка на прототип; число откликов не ограничено | `POST /api/tasks/{id}/proposals` |
| Выбор бизнеса | Список предложений, ручные «выбрать» и «отклонить»; автоназначение запрещено | `POST /api/proposals/{id}/decision` |

## 4. Критерии оценки и чем мы их закрываем

| Критерий | Баллы | Чем закрываем | Владелец |
| --- | :-: | --- | --- |
| Сквозной сценарий | 20 | Все 8 шагов в UI, переключатель ролей, сброс демо-данных одной кнопкой | A + B |
| Качество карточки | 15 | 10 полей; вопросы по недостающим полям в порядке веса; редактирование любого поля; ручное подтверждение | A (AI) + B (редактор) |
| **Геймификация бизнеса** | **25** | Детерминированная формула из 18 прозрачных проверок; подсказки «+N баллов»; уровни; прогноз места в каталоге; история роста; ачивки | A (движок) + B (UI) |
| Каталог и отклики | 15 | Каталог не скрывает задачи; сортировка по рейтингу; фильтры; отклики без лимита; ручное решение бизнеса | A + B |
| AI-функция | 10 | Структурированный вывод, цитаты-доказательства, защита от выдуманных фактов, цепочка fallback, AI Inspector, eval-метрики | A |
| Техническое качество | 10 | README, запуск одной командой, тесты рейтинга, валидация, офлайн-режим | A + B |
| Демонстрация | 5 | Отрепетированный 5-минутный сценарий на заготовленном примере | B ведёт, A страхует |

Самый дорогой критерий — геймификация (25). Рейтинг должен быть прозрачным, пересчитываться на глазах и двигать задачу в каталоге.

## 5. Требования к AI и наши механизмы

| Требование кейса | Механизм |
| --- | --- |
| Минимум одна содержательная AI-функция | Анализ черновика с уточняющими вопросами и сборка карточки из ответов (обе функции) |
| Если внешний API недоступен, допустима заглушка, но нужно показать промпт, формат входа и выхода, обработку некорректного ответа | Офлайн-заглушка в конце цепочки провайдеров; страница AI Inspector показывает промпт, JSON-схему, сырой ответ, ошибки валидации и repair |
| ИИ не добавляет фактов, которых не сообщал пользователь | У каждого поля есть дословная цитата-доказательство; grounding-проверка отбрасывает поля без цитаты, а также числа и контакты, которых нет в исходном тексте |
| Текст редактируется и подтверждается человеком до публикации | Поля от AI имеют статус `suggested`, дают 0 баллов и не публикуются, пока их не подтвердили |
| ИИ может рекомендовать задачи студентам, но не ограничивает каталог | Рекомендации на отдельной вкладке, только для задач с рейтингом от 40; каталог от них не зависит |
| ИИ не выбирает команду за бизнес | Нет ни одного эндпоинта или фоновой логики автоназначения; решение принимается только явным действием бизнеса; AI не ранжирует отклики |
| Персональные и чувствительные признаки не используются | Профиль команды: название, интересы, навыки, технологии. Email, телефоны и @-ники маскируются перед отправкой во внешний API |

## 8. Правила площадки, которые влияют на работу

- **Каждый участник должен внести личный вклад**, иначе участие не засчитывается. Оба коммитят со своих GitHub-аккаунтов, у каждого своя зона (`docs/team/`).
- **Проект должен быть создан в рамках хакатона.** До старта — только планирование и документы, код пишем после старта.
- Выходы суммарно не больше 60 минут. Перед выходом и после возвращения сообщаем стюарду и сканируем бейдж.
- **Весь последний час оба обязаны быть в зале**, выходить нельзя. Сдачу и прогон демо планируем на это время.
- После старта пересаживаться нельзя, в том числе внутри сектора.
- По техническим вопросам поднимаем руку, подойдёт ментор.

## 9. Безопасность (обязательна и влияет на архитектуру)

- **Раздавать интернет с телефона или ноутбука запрещено.** Если сеть площадки упадёт, другой не будет. Поэтому MVP обязан работать офлайн: `AI_PROVIDER=stub`, эмбеддинги TF-IDF.
- Ключи и токены не попадают в код, репозиторий, презентации и чаты. Храним их только в `.env`, который внесён в `.gitignore`. Перед каждым push проверяем репозиторий на секреты (команда в `AGENTS.md`).
- Репозиторий приватный: доступ только у команды и организаторов.
- Не используем реальные продуктивные или персональные данные. Во внешние AI-сервисы не отправляем конфиденциальное: у нас маскирование PII и режим своей модели на Brev.
- Код от AI проверяем сами на безопасность и корректность.
- Нельзя сканировать сеть, устраивать нагрузочные тесты и обходить лимиты.
- Если ключ утёк, сразу сообщаем организаторам и перевыпускаем. После хакатона удаляем временные ключи, токены и локальные копии материалов.

## 11. Оборудование и сеть (чек-лист до выезда)

- Ноутбук и зарядка, зарядка для телефона, мышь и гарнитура по желанию.
- Переходник USB или USB-C → RJ-45, если нет Ethernet-порта. Драйвер ставим и проверяем заранее.
- IP и DNS получаются автоматически (DHCP). Проверка: `ipconfig`; адрес `169.254.x.x` означает, что сеть не выдала IP.
- Крупные обновления ОС ставим заранее, не в день хакатона.
- Заранее установить и хотя бы раз запустить: Git, IDE, Python 3.11 и uv, Node.js и npm, Docker (по желанию), Codex. Войти в GitHub, ChatGPT и NVIDIA.

## 12. Сдача

1. Итоговый код — в командном репозитории `BAITC-Hacks/hack-4b695b60-ai-just` (выдан платформой).
2. README по требованиям организаторов: что делает проект; что реализовано; технологии и архитектура; установка и запуск; пример проверки; данные и внешние сервисы; известные ограничения; ссылка на развёрнутую версию, если есть. Кейс дополнительно требует формулу рейтинга, правила каталога и тестовые сценарии.
3. На платформе: страница треков → наш кейс → «Сдать решение» → название и описание. Обновлять можно до дедлайна.
4. Демо до 5 минут на одном заранее подготовленном примере (`docs/demo-script.md`).

Промпт организаторов для финального README (вставить в Codex в конце, когда код готов):

> Проанализируй текущий проект и создай для него полноценный README.md на русском языке. README должен быть понятен жюри хакатона и содержать: 1. Название проекта 2. Краткое описание — какую проблему решает проект и для кого. 3. Что реализовано — основные функции и возможности решения. 4. Как работает решение — кратко опиши основной пользовательский сценарий от входных данных до результата. 5. Технологии — языки, фреймворки, библиотеки, AI-модели, API и внешние сервисы. 6. Архитектура проекта — основные компоненты и как они взаимодействуют. 7. Установка и запуск — пошаговая инструкция с необходимыми командами. 8.
